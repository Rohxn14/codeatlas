# T17b plan: C, C++ and Rust profiles

Following `.claude/skills/add-language/SKILL.md` once per language. Findings from step 1
(checking the grammar and tags query) shape the plan:

- **C and C++ produce no calls at all**: the upstream tags queries only tag definitions.
  Each needs `queries/<language>/extra.scm` with call patterns (`f()`, `s.f()`, `p->f()`,
  and for C++ `ns::f()` and `f<T>()`).
- **C++ namespaces are invisible**: `namespace ns { int f(); }` gives the key `f`. Tagging
  `namespace_definition` as a scope (`@definition.module`, as Rust's `mod` already is) in
  `cpp/extra.scm` makes it `ns.f`, which `ns::f()` can then be checked against.
- **Prototypes are nodes**: `int f(int);` in a header and `int f(int a) {...}` in the
  source are both tagged as functions, with spans covering only the declarator. Nothing in
  the node says which one has a body.
- **`.h` is C** in the extension table, so a C++ file including `x.h` reaches a C file;
  the C/C++ profile looks up both languages.
- Rust calls work already (`extra.scm` added `Point::new()`); Rust has no imports query.

## Shared resolver changes (no language names)

1. `Profile.reaches()` returns a list (default `[reach()]`): one Rust `use a::{B, c::D}`
   brings several names from several files, which one `Reach` cannot express.
2. `Profile.qualify(ctx, file, call)`: a path written in the call (`crate::util::f()`,
   `Self::new()`, `std::fs::read()`) that is not an import binding.
3. `Profile.narrow(ctx, file, call, nodes)`: drops candidates a language knows are wrong
   (C++ namespace mismatch) or duplicates (a C prototype when its definition is found).
4. `StructuralResolver.set_repo_root()` so the C profile can read `CMakeLists.txt` and
   tell a prototype (`;` after the declarator) from a definition (`{`).
5. `_owner_name` falls back to the node's `receiver` attr (Rust `impl C` in a file where
   `struct C` is not declared has no `owner_key`).

## C and C++ (`structural/c.py`, one module, `CProfile` and `CppProfile`)

- **Import form**: `#include "x.h"` (target `x.h`) and `#include <x>` (target `x`; the
  `<>` form is told apart by an `@import.alias` of `<`).
- **Reach**: quoted: relative to the including file, then include folders (`include/`,
  `src/` in the file's directory and each ancestor, then `include_directories` /
  `target_include_directories` folders from every `CMakeLists.txt`, read as text), then a
  unique path-suffix match anywhere. Angle: include folders only, else external. No
  binding; every name unqualified (`names=None`).
- **Scope**: own file, then the same-named header/source (`x.h` with `x.c`/`x.cpp`, same
  folder, or the only such file in the repository).
- **narrow**: a prototype candidate is swapped for the definition in its header's source
  file; `ns::f()` keeps only candidates whose namespace/class path ends with `ns`.
- **Expect wrong**: includes are not transitive (a header included by a header falls back
  to a name guess); macros and function pointers stay unresolved; calls to libc are not
  edges (no header says which names it declares); C++ classes in `.h` files are parsed as C.

## Rust (`structural/rust.py`)

- **Import form**: `use` in every shape (path, `as`, `{...}` lists, `*`), `mod x;`
  (reported with alias `mod`) and `extern crate`.
- **Reach**: walk the path: `crate` from the crate root (T15 Cargo package: `library`
  attr or `src/main.rs`; a file under `src/bin`, `tests`, `examples` is its own root),
  `self`/`super` relative to the file's module, a child module (`x.rs` or `x/mod.rs`), a
  workspace crate by name (`-` and `_` equal), else external. Remaining segment: an item;
  a type gives `binding` and `class_name`, a function gives `names`. Re-exports
  (`pub use`) are followed up to 5 hops.
- **Scope**: the file only (Rust has no package scope); bare calls are top-level only.
- **qualify**: `a::b::f()`, `Self::new()`, `crate::x::f()`; lowercase unknown first
  segment = external crate; prelude types (`Vec`, `String`, ...) external.
- **Expect wrong**: `use super::*` inside `mod tests { }` resolves to the parent of the
  file, not the file (the import carries no enclosing-module information; own-file lookup
  comes first so calls still resolve); trait methods via method syntax on a variable are
  guesses; `impl C` in a file not reached by the import is missed; macros unresolved.

Cut-off: 5 candidates, as everywhere. Real repositories: `jqlang/jq` or `antirez/kilo`
(C), `nlohmann/json` or `fmtlib/fmt` (C++), `BurntSushi/ripgrep` or `rust-lang/log` (Rust).
