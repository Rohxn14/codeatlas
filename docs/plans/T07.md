# T07 plan: TypeScript and JavaScript resolver

## Approach

One class, `TypeScriptResolver`, in the package `languages/typescript/resolver/`. The pipeline hands it the `ParseResult`s of `typescript`, `tsx` and `javascript` and a `SymbolIndex`. Everything it needs about *code* is in those results, so it builds its own in-memory tables and does not query the store per call:

- `Tables`: key -> Node, top-level symbols per file, members per class, name -> nodes (for guesses).
- `ModuleResolver` (`modules.py`): a specifier plus the importing file -> a repo path, or "external". It holds the set of repo paths, the tsconfig settings (`tsconfig.py`) and the workspace packages (`packages.py`).
- `ExportTable` (`exports.py`): what a file exports, with re-export following (cycle guard, five hops).
- `Bindings` (`bindings.py`): per file, local name -> what an import bound it to (symbol, module, namespace, external).
- `calls.py` applies the levels; `inherits.py` and the TESTS projection are small.

Gap found: `Resolver.resolve(results, index)` gives no file access and no repository root, but tsconfig and `package.json` are files. The resolver takes an optional `read_file` callable; without one it finds the root from the snapshot source in the store when that is a local folder. For a GitHub URL (a temporary clone) tsconfig `paths` and `exports` are then off, and relative imports, barrels and calls still work. The smallest real fix is for the pipeline to give resolvers the root (reported in the PR, not done here: `plugins.py` and the pipeline are outside my folder).

## Rule for each level (fixture example)

| Level | Rule | Example |
| --- | --- | --- |
| IMPORTS, STRUCTURAL 1.0 | specifier resolved, name looked up through re-exports | `UserList.test.tsx` -> `components/UserCard.tsx::UserCard`; `client.test.ts` importing `UserApi` from `../src/api` goes to `client.ts::UserApi`, not `index.ts` |
| DIRECT 1.0 | name defined in the file or bound by an import; `ns.f()`; JSX | `<UserCard />` in `UserList` -> `UserCard` |
| SELF_METHOD 0.9 | `this.m()` / `super.m()`, class then bases through imports | `UserApi.getUser` -> `this.remember()` |
| IMPORT_SCOPED 1/n | receiver unknown; `name` defined in the file or the files it imports (through barrels) | `api.getUser(7)` in the test: one `getUser` in the imported files |
| NAME_GUESS min(0.3, 1/n) | otherwise, same name anywhere in TS/JS files | none on the fixture; a unit test covers it |
| INHERITS | `bases` resolved like names | `UserApi` -> `types.ts::UserSource` |
| TESTS | each CALLS edge from a TEST node to a non-test function, same resolution and confidence | test -> `UserApi.getUser` |

## Decisions

1. **Typed receivers.** Neither the adapter nor RawCall carries variable types, so `api.getUser(7)` arrives as "receiver `api`, type unknown". I treat a typed receiver and an unknown one the same: IMPORT_SCOPED, 1/candidates. Why: it is honest (we did not read the type) and equals 1.0 when the method name is unique among imported files. If T06 chose a higher level for declared types, I would add a type table to the adapter output (a contract change) and use SELF_METHOD-like 0.9.
2. **Name-guess cut-off.** More than 5 candidates: no edge. (`docs/decisions.md` Q2 is unanswered.) Why: at 6 candidates each edge is at most 0.17 and mostly noise; the impact engine would rank them below everything anyway.
3. **Mixed JS and TS.** Yes: `typescript`, `tsx`, `javascript` count as one family for guesses and for imports, since a `.js` file really does import `.ts` files in mixed repositories.
4. **Globals** are `::external:globals.<callee as written>` (`globals.console.log`), a set of about 60 well-known names, used only when nothing binds the name.
5. **Default import** goes to the symbol named `default`; if the file has none, to the file's module (the adapter does not say which class is the default export).

## Tests

Samples in `tests/data/typescript_resolver/` parsed by the real adapters, exact edge lists: every specifier form, tsconfig with comments, trailing comma, `extends`, `baseUrl`, `paths`; a workspace package with `exports`; a barrel chain of two hops and a cycle; default and namespace imports; `require`; `this.m()` inherited; JSX; written and unwritten constructor; globals; external call; name guess and its cut-off; INHERITS; TESTS. Plus one run through `build_graph` on a temporary folder.

## Expect to get wrong

Calls on values whose type matters (`cache.get` where `get` is also user-defined), `export { a as b }` without `from` (the adapter emits no raw item), callbacks and dynamic property access, a `default` class whose name differs from its import, package `exports` conditions beyond `import`/`default`/`types`, and everything under tsconfig `paths` when the root cannot be found.
